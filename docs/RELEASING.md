# 发布怎么跑

改 `Cargo.toml` 里的 `workspace.package.version`，合进主干。就这一步。

之后：verify 在主干上跑完 → `.github/workflows/release.yml` 被 `workflow_run` 拉起 →
它判定要不要发 → 三平台构建并打包 → 打 tag、建 Release、上传附件 → 回查附件。

## 三个不会报错的形状，各配一条断言

1. **发了一份没过闸门的树。** 「发布了」与「验过了」在页面上长得一模一样。
   所以触发源是 verify 跑完，并且要求 conclusion 是 success、head_branch 是主干。
   手动触发（workflow_dispatch）走同一个门禁，只是改成主动去问 API 要结论 ——
   手动就免检的话，那个门禁等于没有，而手动恰好是最容易被用的那条路。
2. **Release 建出来了而附件没上去。** 下载的人看到一个空发布，而 CI 是绿的。
   所以发完会回查一次：附件数必须等于平台数，且 tag 必须真的指向那个提交。
   上传前还先数一次包：少了平台就不发，一个只有两个平台的 Release
   与完整的那个长得一模一样。
3. **重复发布。** 循环终止靠 tag 身份（`v<版本>` 已存在就跳），不靠提交信息字符串：
   字符串守卫改一次模板就哑，而哑掉的表现不是红。

版本号只有一份真身（Cargo.toml），流水线里不得抄。有一条负向断言盯着这一点。
平台数与 `EXPECTED_ASSETS` 是一组耦合参数，有等号断言钉着：只改矩阵不改期望数的话，
第四个平台会静默被丢掉而发布仍然绿。

## 没有自动断言守住的那一半

**流水线根本没触发时，没有任何东西会开口。** 它与「没有新版本要发」在面板上
一模一样，而 `workflow_run` 是一种条件触发（它只从默认分支上的工作流文件生效）。

能做的只是保证**跑了就一定留下痕迹**：无论发还是跳，都会回写一条带
`trigger` / `head_sha` / `version` / `why` / `run_id` 的评论（marker：发布原始输出）。
于是人可以读出一个信号：**主干绿了但没有那条评论 ≡ 发布流水线没跑。**

同类型的坑已经在 format.yml 上真实发生过一次（job 级 `env:` 里用了 `runner.temp`，
整份工作流无法加载、一次也没跑，而我读到的一直是上一轮的旧评论）。
详细经过写在 docs/FORMATTING.md 里。

## 发布说明里必须写清机器验不到什么

一份只写好消息的发布说明会让人以为一切都验过了。现在每次发布都带上：

- macOS / Windows 屏幕上的真实界面（截图只在 Linux 上拍）
- 输入法的真实行为（候选框位置、转换段、删周围字符）
- macOS 风格像不像原生、滚动手感、字体观感

这三条与 docs/PITFALLS.md 的「测不出来」一节是同一件事，有一条断言要求发布说明里
必须出现「人工验收」与指向那份档案。

## 我做不了的部分

- 删除 tag 或 Release、改仓库可见性、改默认分支、开「合并后自动删分支」。
- 带签名的 tag / 产物签名（需要密钥进仓库 secrets）。
- 安装包（.dmg / .msi）与公证、应用商店提交：需要证书与人工审核。
