# 已知限制与实测记录

## 目前的限制

- 大文件模式（> 64 MB）是**只读**的：只建行索引 + 按需读窗口，搜索与替换走磁盘流式路径。
  不假装可以内存编辑：假装的代价是用户敲了一下键才发现改不了，而那时候他已经信任它了。
- 大文件模式不回溯跨行高亮状态：从文件中间开始看时，块注释内的代码会染成普通色。
  要准就得从文件头扫到当前行。
- `find_before`（向上查找）是从头正扫，超大文件上是 O(n)，不是 O(1)。
- 非 ASCII 大小写折叠不做完整 Unicode case folding（只折叠 ASCII）。
- 内存编辑器里含换行的模式一律返回零个匹配；跨行替换请走文件级流式路径。
- macOS 上中文可能显示为豆子块：系统自带的中文字体都是字体集合（.ttc），
  而当前只接受 .ttf/.otf（字体集合在部分环境下会直接 panic，而一个启动就挂的编辑器
  比一个显示豆子块的编辑器糟得多）。

## 踩过的坑

- **macOS runner 的 /bin/bash 是 3.2.57（2007 年）。** 一句多行 printf + 命令替代在它上面
  把变量名读坏了，`set -u` 把它变成硬错。症状极具欺骗性：**评论已经成功发出去了，
  job 才红**，且三个平台里只有一个红，看起来像平台特有的网络或权限问题。
  现在有 `crates/meta/tests/portable_shell.rs` 守着。
- **`permissions:` 一写就变白名单。** 没列的范围全部变 none；没给 `actions: read`
  导致下载产物静默挂掉，而报告里只看得到「未确认」。
- **CI 的运行日志没有工具读得到。** 红了之后手里只有一个比特，只能二分推送去猜。
  修法不需要新能力：把原始输出贴成评论，每个平台一个 marker。包括**回写脚本自己的
  错误输出**——观察者不能是被观察的那个，所以第一次调用的 stderr 由第二次调用带出来。
- **egui/eframe 0.36 改了应用模型。** 入口是 `App::ui(&mut Ui)` 而不是 `update(&Context)`，
  面板的 `show` 也收 `&mut Ui`；`Context::fonts` 给的是不可变引用，排版要走 `Painter`。
- **字节串字面量里不能写非 ASCII**（`b"中文"` 直接编译不过），用 `"…".as_bytes()` 或十六进制转义。
- **按单文件判的「剥完还剩四成」是一台假红工厂。** consts.rs 本来就是注释占大头（故意的），
  改成聚合判并打印实测值。

## 测不出来

- 真实 GPU / 真机体验：CI 里跑的是软件渲染，只能证明「窗口真的画出了内容」，
  证明不了滚动手感、字体观感、极简风格好不好用。这部分只能人工验收。
- macOS / Windows 上的真实运行：目前只验了编译与打包，截图与基准只在 Linux 上跑。
  （不是测不了，是还没接；接上去需要先确认那两个 runner 能不能起无头窗口。）
- 每月的 CI 额度花费：用量页面只有人打得开。已知的只有计费规则（macOS 十倍、
  Windows 两倍、按 job 向上取整到分钟），具体金额只能是估算区间，不当实测写。

## 阈值实测值

下面都是 CI（ubuntu-latest、软件渲染、共享 CPU）上的实测值。
性能类阈值只用来抓「彻底卡死 / 白屏 / 死循环」，不当性能基准。

| 项 | 实测值 | 现在的阈值 | 它只抓哪一类失败 |
| --- | --- | --- | --- |
| 截图尺寸 | 1280x800 | 必须是 1280x800 的整数倍 | 窗口根本没按请求尺寸创建 |
| 不同颜色数 | 3063 / 3055 | ≥ 1000 | 空窗口，没真的画出高亮文本 |
| 背景色占比 | 0.9641 / 0.8980 | ≤ 0.995 | 一张纯色图 |
| 64 MB 建行索引 | 77 ms | < 3000 ms | 索引卡死 |
| 64 MB 全文搜索 | 37 ms | < 3000 ms | 搜索卡死 |
| 64 MB 流式替换 | 81 ms | < 5000 ms | 替换卡死 |
| 64 MB 写盘 | 33 ms | 无 | — |
| 1,040,619 行的埋点 | 2082 个 | 搜到与替掉必须都等于 2082 | 少替一个（这一条是正确性，不是性能） |

性能阈值故意给到约 40 倍余量（不是三倍）：共享 CPU 的 runner 抖动很大，
留三倍会变成一台假红工厂，而假红会让人学会忽略闸门。
