# 带期限的义务

「等下次顺手做」是这类项目里最常见的谎。这里的每一条都有期限，完成判据读代码而不是读我的报告，
并且由 `crates/meta/tests/obligations.rs` 守：完成了还挂着也判红，因为一份挂着已完成事项的清单没人会再读。

## OB-1 让 cargo fmt 变成阶断项

- deadline: 2026-09-26（unix 1790380800）
- 为什么现在不阶断：V1 的代码是在没有 Rust 工具链的环境里手写的，首轮一定一大片格式差异。
  把它直接设成阶断会让真正的行为失败淹在几百条缩进差异里。
- 完成判据（读代码，不读报告）：`scripts/verify.sh` 的**可执行代码**里出现格式阶断那一步。
  判据必须先剥 shell 注释：实测踩过一次——我在注释里解释了一句那个判据是什么，
  于是一条根本没做完的义务被认定为已完成，而那会逐人把它从清单上删掉。
- **fmt 欠账的实测值与上限**：最近一次实测 `fmt_diff_lines=100`（run 33993683456，
  rustfmt 1.9.0-stable），上限 110。实测值是**快照**，不是被钉住的数：
  它每加一份手写代码就会动，给它配等号断言只会变成一台假红工厂。
  被钉住的只有上限那一个数：它写在 `scripts/verify.sh` 的 `FMT_CEILING`，
  与本文由一条等号断言钉着，只改一头会红。
- 为什么需要那个上限：这笔欠账实测从 28 一路涨到 100，而**涨的过程每一轮都是绿的**。
  一个只写在文档里的欠账会静默变大，所以现在它只能往下走（棘轮）。
  棘轮不等于本条义务已完成：它守的是「不得再变差」，不是「已经归零」。
- 110 这个余量是**拍的**，且只给 rustfmt 版本漂，不给新敲的代码。因为这两个原因在一个
  孤零的数字上长得一模一样，报告里同时带 `rustfmt_version`。
  现在只剩 10 的余量，也就是说**下一份手写的 Rust 文件很可能直接把它撞红**。
  那时候正确反应不是把上限往上调，而是在一个有 rustfmt 的环境里跑一遍把它压下去。
- 到期只有两个正确反应，都不是把日期往后挑：要么真的做完了（删掉本条），
  要么确认做不到（挑进 docs/PITFALLS.md 的「测不出来」）。
- 属于哪种义务：**一次性**。履行后直接删掉本条就对，因为它的完成判据本身就会变成一条常驻断言（fmt 阶断）。

## 不登记成义务的事（有理由的记录）

- **macOS / Windows 上的无头截图。** 目前只在 Linux 上跑截图与基准。要不要接上去，
  取决于那两个 runner 能不能稳定地起一个无头窗口，而这个得先跑一次才知道；
  它也直接进计费（macOS 十倍）。先写成记录，不假装它有截止日。
  在那之前，那两个平台能自动验的上限就是字体探测（不开窗口），屏幕上的事要人拍图。
- **上游 egui 对字体集合的支持细节。** 选脸（face index）现在自己解 cmap 挑，
  因为上游不告诉我哪张脸覆盖中日韩字。上游往后如果提供了覆盖查询，这一层就能变薄；
  时机不由我定，所以不给它定期限。
